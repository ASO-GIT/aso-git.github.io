Bloque 1: Registros de Imágenes Docker

Conceptos de registros

Docker Hub vs Artifact Registry

Publicación manual de imágenes

Autenticación y mejores prácticas

Este bloque introduce los conceptos de registros de imágenes y cómo publicar imágenes en diferentes plataformas.

¿Qué son los Registros de Imágenes?

Repositorios centralizados para almacenar imágenes Docker

Permiten compartir imágenes entre equipos y entornos

Facilitan la distribución de aplicaciones contenedorizadas

Integración con servicios cloud y CI/CD

Los registros son esenciales para el flujo de trabajo de contenedores. Sin registros, cada desarrollador tendría que construir imágenes localmente.

Tipos de Registros

Públicos

  • Docker Hub
  • GitHub Container Registry
  • Acceso abierto
  • Ideal para open source

Privados

  • Artifact Registry (GCP)
  • ECR (AWS)
  • ACR (Azure)
  • Control de acceso granular
Distinguir entre registros públicos y privados. Los privados ofrecen mejor seguridad y control.

Docker Hub

  • Registro público más utilizado
  • Acceso gratuito para imágenes públicas
  • Planes de pago para imágenes privadas
  • Formato: usuario/imagen:tag
  • Ideal para proyectos open source
Docker Hub es el punto de partida para la mayoría de desarrolladores. Es simple pero tiene limitaciones en planes gratuitos.

Google Container Registry (GCR)

  • Servicio original de GCP
  • Utiliza Cloud Storage como backend
  • Formato: gcr.io/PROJECT_ID/imagen:tag
  • En desuso - Migrar a Artifact Registry
GCR está siendo reemplazado por Artifact Registry. Mencionar pero enfatizar que Artifact Registry es el futuro.

Artifact Registry

  • Servicio moderno de GCP
  • Soporta múltiples formatos (Docker, Maven, npm)
  • Control de acceso mediante IAM
  • Formato: REGION-docker.pkg.dev/PROJECT_ID/REPO/IMAGE:TAG
  • Mejor integración con servicios GCP
Artifact Registry es el servicio recomendado para nuevos proyectos en GCP. Ofrece mejor integración y más características.

Comparativa: Docker Hub vs Artifact Registry

Característica Docker Hub Artifact Registry
Público/Privado Ambos Privado
Integración GCP Limitada Nativa
Control de acceso Básico IAM granular
Costo Gratis (limitado) Pay-per-use
Comparar ambos servicios para ayudar a los estudiantes a decidir cuándo usar cada uno.

Publicación en Docker Hub


# 1. Autenticarse
docker login

# 2. Construir imagen
docker build -t app-info-service:latest .

# 3. Tagging con formato Docker Hub
docker tag app-info-service:latest \
  usuario/app-info-service:latest

# 4. Publicar
docker push usuario/app-info-service:latest
Mostrar el proceso paso a paso. Enfatizar la importancia del formato correcto del tag.

Publicación en Artifact Registry


# 1. Habilitar API
gcloud services enable artifactregistry.googleapis.com

# 2. Crear repositorio
gcloud artifacts repositories create docker-repo \
  --repository-format=docker \
  --location=europe-west1

# 3. Configurar autenticación
gcloud auth configure-docker \
  europe-west1-docker.pkg.dev

# 4. Tagging y push
docker tag app-info-service:latest \
  europe-west1-docker.pkg.dev/PROJECT_ID/docker-repo/app-info-service:latest

docker push europe-west1-docker.pkg.dev/PROJECT_ID/docker-repo/app-info-service:latest
El proceso es similar pero requiere configuración previa de GCP. El formato del tag es más largo pero más descriptivo.

Mejores Prácticas de Tagging

  • Usar tags semánticos: v1.2.3
  • Tag latest para versión más reciente
  • Tags basados en commit SHA para trazabilidad
  • Evitar tags genéricos como dev, test
  • Documentar estrategia de versionado
El tagging correcto es crucial para gestión de versiones y rollbacks. Enfatizar la importancia de una estrategia clara.

Bloque 2: Cloud Build - Automatización CI/CD

Conceptos de CI/CD

Configuración de cloudbuild.yaml

Triggers automáticos

Integración con Artifact Registry

Este bloque introduce la automatización mediante Cloud Build, eliminando la necesidad de builds manuales.

¿Qué es CI/CD?

CI - Continuous Integration

  • Integración frecuente de código
  • Builds y tests automatizados
  • Detección temprana de errores
  • Código siempre funcional

CD - Continuous Deployment

  • Despliegue automatizado
  • Publicación de artefactos
  • Despliegue en producción
  • Reducción de errores manuales
Explicar los beneficios de CI/CD: velocidad, calidad y confiabilidad.

Cloud Build

  • Servicio completamente gestionado de GCP
  • Ejecuta builds en la nube
  • Sin infraestructura propia
  • Integración nativa con servicios GCP
  • Escalable y confiable
Cloud Build elimina la necesidad de mantener servidores de CI/CD propios. Todo se gestiona en la nube.

Arquitectura de Cloud Build

  • Builds ejecutados en contenedores efímeros
  • Cada paso en un contenedor específico
  • Pasos ejecutados secuencialmente
  • Build falla si cualquier paso falla
  • Logs disponibles en Cloud Logging
La arquitectura basada en contenedores permite usar cualquier herramienta en cada paso del build.

Estructura de cloudbuild.yaml


steps:
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'imagen:tag', '.']
  
images:
  - 'imagen:tag'
  
substitutions:
  _VARIABLE: 'valor'
  
options:
  machineType: 'E2_HIGHCPU_8'
  
timeout: '1200s'
Mostrar la estructura básica. Cada sección tiene un propósito específico.

Ejemplo: cloudbuild.yaml Completo


steps:
  # Paso 1: Construir imagen
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'build'
      - '-t'
      - '${_REGION}-docker.pkg.dev/${PROJECT_ID}/${_REPO_NAME}/app:${SHORT_SHA}'
      - '-t'
      - '${_REGION}-docker.pkg.dev/${PROJECT_ID}/${_REPO_NAME}/app:latest'
      - '.'
  
  # Paso 2: Publicar imagen
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'push'
      - '--all-tags'
      - '${_REGION}-docker.pkg.dev/${PROJECT_ID}/${_REPO_NAME}/app'

images:
  - '${_REGION}-docker.pkg.dev/${PROJECT_ID}/${_REPO_NAME}/app:${SHORT_SHA}'
  - '${_REGION}-docker.pkg.dev/${PROJECT_ID}/${_REPO_NAME}/app:latest'

substitutions:
  _REGION: 'europe-west1'
  _REPO_NAME: 'docker-repo'
Mostrar un ejemplo completo y funcional. Explicar cada parte en detalle.

Variables en Cloud Build

Automáticas

  • PROJECT_ID
  • SHORT_SHA
  • COMMIT_SHA
  • BRANCH_NAME

Personalizadas

  • Prefijo _
  • Definidas en substitutions
  • Pueden pasarse externamente
  • Útiles para diferentes entornos
Las variables permiten parametrizar builds. Las automáticas proporcionan información del contexto del build.

Ejecutar Build Manualmente


# Desde directorio con cloudbuild.yaml
gcloud builds submit --config cloudbuild.yaml

# Con substitutions personalizadas
gcloud builds submit --config cloudbuild.yaml \
  --substitutions=_REGION=us-central1

# Ver builds recientes
gcloud builds list --limit=10
Los builds manuales son útiles para testing antes de configurar triggers.

Triggers de Cloud Build

  • Ejecutan builds automáticamente
  • Responden a eventos de Git
  • Push a ramas específicas
  • Creación de tags
  • Pull requests
Los triggers eliminan la necesidad de ejecutar builds manualmente. Cada push puede disparar un build automático.

Configurar Trigger

  • Conectar repositorio Git a Cloud Build
  • Definir evento (push, tag, PR)
  • Especificar rama o patrón
  • Seleccionar archivo cloudbuild.yaml
  • Configurar substitutions opcionales
Los triggers pueden configurarse mediante consola o CLI. Mostrar ambos métodos si es posible.

Flujo Completo CI/CD

  1. Desarrollador hace push a Git
  2. Trigger detecta el cambio
  3. Cloud Build ejecuta build
  4. Imagen se construye y publica
  5. (Opcional) Despliegue automático
Mostrar el flujo completo desde código hasta producción. Este es el objetivo final de CI/CD.

Bloque 3: Cloud Run - Serverless Containers

Conceptos de serverless

Despliegue en Cloud Run

Configuración avanzada

Escalado automático

Este bloque introduce Cloud Run, permitiendo ejecutar contenedores sin gestionar servidores.

¿Qué es Serverless?

  • Modelo de ejecución sin gestión de servidores
  • El proveedor gestiona infraestructura
  • Escalado automático
  • Facturación por uso
  • Sin costo cuando no hay tráfico
Serverless cambia el modelo de pago: de servidores siempre activos a pago por uso real.

Cloud Run

  • Servicio serverless de GCP
  • Ejecuta contenedores Docker
  • Escalado automático desde cero
  • Facturación por petición y tiempo de ejecución
  • Soporta HTTP/HTTPS y gRPC
Cloud Run combina la flexibilidad de contenedores con la simplicidad de serverless.

Arquitectura de Cloud Run

  • Instancias efímeras creadas bajo demanda
  • Múltiples peticiones por instancia (concurrency)
  • Escalado horizontal automático
  • Load balancer gestionado
  • Health checks automáticos
Cloud Run gestiona todo automáticamente: creación de instancias, distribución de carga, health checks.

Contrato de Cloud Run

La aplicación debe:

  • Escuchar en puerto definido por variable PORT
  • Responder a peticiones HTTP
  • Implementar endpoint de health check
  • Ser stateless (sin estado local)
  • Manejar shutdown gracefully
El contrato de Cloud Run es simple pero importante. Las aplicaciones deben seguir estas reglas.

Despliegue Básico


# Desplegar desde imagen existente
gcloud run deploy app-info-service \
  --image europe-west1-docker.pkg.dev/PROJECT_ID/repo/app:latest \
  --region europe-west1 \
  --platform managed \
  --allow-unauthenticated

# Desplegar desde código fuente
gcloud run deploy app-info-service \
  --source . \
  --region europe-west1 \
  --allow-unauthenticated
Mostrar ambos métodos de despliegue. El método desde código fuente es más simple pero menos controlable.

Variables de Entorno


# Durante despliegue
gcloud run deploy app-info-service \
  --set-env-vars "APP_NAME=Mi App,ENVIRONMENT=production"

# Actualizar servicio existente
gcloud run services update app-info-service \
  --set-env-vars "APP_NAME=Mi App,ENVIRONMENT=production"
Las variables de entorno son útiles para configuración no sensible. Para secretos, usar Secret Manager.

Configuración de Recursos


gcloud run services update app-info-service \
  --cpu 2 \
  --memory 1Gi \
  --max-instances 10 \
  --min-instances 0 \
  --concurrency 80 \
  --timeout 300
  • --cpu: CPUs asignadas (1-8)
  • --memory: Memoria (128MB-32GB)
  • --concurrency: Peticiones simultáneas por instancia
  • --min-instances: Instancias mínimas (0 = escala a cero)
La configuración de recursos afecta rendimiento y costo. Encontrar el balance correcto es importante.

Escalado Automático

  • Escala desde cero cuando no hay tráfico
  • Crea nuevas instancias bajo demanda
  • Distribuye carga entre instancias
  • Elimina instancias cuando baja la carga
  • Cold start en primera petición después de inactividad
El escalado automático es una de las características más poderosas de Cloud Run. Explicar el trade-off entre costo y cold starts.

Health Checks

  • Cloud Run verifica salud de instancias
  • Endpoint /health por defecto
  • Instancias no saludables no reciben tráfico
  • Reemplazo automático de instancias fallidas

@app.route('/health')
def health():
    return {'status': 'healthy'}
Los health checks son esenciales para que Cloud Run sepa cuándo una instancia está lista para recibir tráfico.

Logging y Monitorización

  • Logs automáticos en Cloud Logging
  • stdout y stderr capturados automáticamente
  • Métricas de peticiones disponibles
  • Trazabilidad de requests

# Ver logs
gcloud run services logs read app-info-service \
  --region europe-west1 --limit=50
Los logs son esenciales para debugging. Cloud Run los proporciona automáticamente sin configuración adicional.

Pricing de Cloud Run

  • Free tier generoso: 2M requests/mes
  • Pago por uso después del free tier
  • Facturación por:
    • Número de requests
    • Tiempo de CPU
    • Memoria utilizada
  • Sin costo cuando escala a cero
El modelo de pricing de Cloud Run es muy favorable para aplicaciones con tráfico variable.

Bloque 4: Secret Manager y Migración

Conceptos de Secret Manager

Integración con Cloud Run

Migración Docker Compose → Cloud Run

Mejores prácticas de seguridad

Este bloque final integra todo lo aprendido y muestra cómo migrar aplicaciones completas a producción.

¿Por qué Secret Manager?

  • Problema: Secretos en código o imágenes
  • Solución: Almacenamiento seguro centralizado
  • Encriptación automática
  • Control de acceso mediante IAM
  • Rotación de secretos facilitada
Secret Manager resuelve el problema común de cómo gestionar secretos de forma segura.

Secret Manager de GCP

  • Almacenamiento seguro de secretos
  • Encriptación en reposo y en tránsito
  • Control de acceso mediante IAM
  • Versionado de secretos
  • Auditoría de acceso
Secret Manager proporciona todas las características necesarias para gestión segura de secretos.

Crear Secretos


# Desde línea de comandos
echo -n "Mi secreto" | \
  gcloud secrets create secret-name \
  --data-file=- \
  --replication-policy="automatic"

# Desde archivo
gcloud secrets create secret-name \
  --data-file=secreto.txt \
  --replication-policy="automatic"

# Listar secretos
gcloud secrets list
Mostrar diferentes formas de crear secretos. Enfatizar la importancia de no dejar archivos con secretos en el sistema.

Versionado de Secretos

  • Cada secreto puede tener múltiples versiones
  • Versiones permiten rotación sin cambiar código
  • Usar :latest para versión más reciente
  • Especificar versión específica para producción

# Acceder a versión específica
gcloud secrets versions access 1 --secret="secret-name"

# Listar versiones
gcloud secrets versions list secret-name
El versionado permite rotar secretos de forma controlada y segura.

Permisos IAM

  • Control granular de acceso
  • Roles específicos para secretos
  • Service accounts para servicios

# Otorgar acceso a Cloud Run
PROJECT_NUMBER=$(gcloud projects describe PROJECT_ID \
  --format='value(projectNumber)')

gcloud secrets add-iam-policy-binding secret-name \
  --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
Los permisos IAM son esenciales para que Cloud Run pueda acceder a secretos.

Integración con Cloud Run

Montar secretos como variables de entorno:


gcloud run deploy app-info-service \
  --update-secrets "SECRET_MESSAGE=secret-message:latest"

Montar secretos como archivos:


gcloud run deploy app-info-service \
  --update-secrets "/etc/secrets/secret=secret-name:latest"
Mostrar ambas formas de montar secretos. Las variables de entorno son más simples, los archivos más seguros.

Migración: Docker Compose → Cloud Run

Desarrollo Local

  • Docker Compose
  • Archivo .env
  • Volúmenes locales
  • Red Docker

Producción

  • Cloud Run
  • Secret Manager
  • Servicios gestionados
  • Red pública
Comparar desarrollo local con producción. La migración requiere cambios pero sigue el mismo Dockerfile.

Proceso de Migración

  1. Preparar aplicación (usar variable PORT)
  2. Migrar secretos a Secret Manager
  3. Configurar Cloud Build
  4. Desplegar en Cloud Run
  5. Configurar CI/CD automático
El proceso de migración es sistemático. Cada paso debe completarse antes del siguiente.

Cloud Build con Despliegue


steps:
  # Construir imagen
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'imagen:tag', '.']
  
  # Publicar imagen
  - name: 'gcr.io/cloud-builders/docker'
    args: ['push', 'imagen:tag']
  
  # Desplegar en Cloud Run
  - name: 'gcr.io/google.com/cloudsdktool/cloud-sdk'
    entrypoint: gcloud
    args:
      - 'run'
      - 'deploy'
      - 'app-info-service'
      - '--image'
      - 'imagen:tag'
      - '--update-secrets'
      - 'SECRET_MESSAGE=secret-message:latest'
Mostrar cómo integrar despliegue en Cloud Build para CI/CD completo.

Mejores Prácticas de Seguridad

  • Nunca hardcodear secretos en código
  • No incluir secretos en imágenes Docker
  • Usar Secret Manager para producción
  • Rotar secretos regularmente
  • Usar versiones específicas en producción
  • Limitar permisos mediante IAM
La seguridad es crítica. Enfatizar estas mejores prácticas en cada oportunidad.
